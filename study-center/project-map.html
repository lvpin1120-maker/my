先记住一句话：管理端管配置，执行引擎跑流程，网关调用模型。

两个仓库，不只有两种职责

你说的“管理端”通常对应 dify-engine 里的 manager 服务。但 dify-engine 仓库还包含 platform 服务，也就是 AI 工作流执行引擎。llm-proxy-moa 是另一个仓库，承担大模型网关职责。先把这三块分开，后面读代码会清楚得多。

管理端 Manager谁能用、用哪些模型、应用配置、版本与发布
配置与发布 →
执行引擎 Platform读工作流，执行节点，传变量，处理分支与结果
需要模型 →
大模型网关 Gateway鉴权、限流、路由、协议适配、调用厂商

这是职责关系图，不表示每次业务调用都必须顺序经过三个服务。业务方可以直接调用网关；管理端也会为了模型测试、生成向量或调试而调用 AI 服务。

1. 管理端：AI 平台的控制后台

它解决的问题：如果每接一个业务、加一种模型、修改配置、发布一个工作流都要直接改代码，维护会很困难。管理端把这些信息和操作组织成后台能力，提供管理、审批、发布和查询入口。

谁用它：管理后台用户、平台运维或业务配置人员，以及需要获取配置的其他服务。它连接 MySQL，提供 MOA RPC 接口，还包含分发和代理能力。

核心功能白话解释你先关心什么
工作空间与 API Key把不同业务的资源和使用身份组织起来空间、业务身份和调用凭证怎样关联；不能只凭表名假设权限已全部落实
供应商与模型登记模型来自哪里、有哪些能力、使用什么配置逻辑模型名、厂商、实际模型、配置与凭证的区别
模型连通测试试着调用一次，判断当前配置能不能用modelPing 怎样选模型、调用谁、失败怎么反馈
应用与版本保存 AI 应用和工作流配置，管理不同版本编辑、创建版本、上线三个动作不应简单视为同一件事
发布、灰度、回滚决定哪份配置让哪些调用方使用配置怎样生效，旧版本与新版本怎样区分
知识库、标注与调试维护检索数据，转发调试、查询运行记录需要学 RAG 和排障时再深入
价格、账单与审批处理平台治理和成本相关业务若非你负责且不写简历，先知道用途，暂不逐接口读

关键纠正：管理端不只是增删改查，它有配置组装、发布和跨服务调用；但它也不应被说成 DAG 执行器。实际 WorkflowRunner 在 platform 服务。

2. 大模型网关：业务调用模型的统一入口

它解决的问题：不同模型厂商的请求格式、鉴权、流式事件和错误不完全一样。如果每个业务直接接所有厂商，就会重复建设。网关提供统一接入，并把配置、调用治理与厂商差异集中处理。

谁用它：业务后端、工作流引擎以及支持兼容协议的调用端。网关不是训练大模型的服务，也不能因入口叫 AgentController 就推断它运行了完整 Agent 规划循环。

厂商调用与返回协议转换、响应／SSE、错误、用量与指标

第一次读代码的完整主线：AgentController → ProtocolCommon → Pipeline.process → Auth → Limit → ModelRouter → ProviderMoaiClient → Processor → 某一个具体模型调用。

Controller 是 HTTP 入口；Pipeline 是编排服务；Processor 是处理抽象／实现；它们不是三个对外 HTTP 接口。先分清“外部接口”和“内部方法”。

3. 工作流执行引擎：把多个步骤串起来运行

如果业务需求是“检索知识→拼提示词→问模型→处理结果→返回”，单次模型调用不够。platform 服务读取工作流配置，建立节点与依赖，运行节点，传递变量，处理并发、失败、超时和结果。

例子：用户问报销规则 → Start 接收输入 → Knowledge 检索规则 → LLM 基于规则生成回答 → End 输出。这个例子用于理解，不代表已经确认生产存在这条具体流程。

节点需要模型时，可以通过模型适配层调用网关；不是所有节点都调用网关。代码节点、变量处理或其他工具节点可以有不同执行路径。

优先级Controller 路径／内部入口阅读目的
第一批POST /v1/workflows/runDifyEngineController.workflowRun：一般工作流运行入口
第一批POST /v1/chat-messages聊天应用请求入口；与普通模型 chat/completions 不是同一层
第一批WorkflowRunner.build、runWithTaskId、run(state,node)配置构建、一次执行状态、节点调度
第一批WorkflowRunState、VariablePool、BaseNode当前执行的状态、变量与节点公共逻辑
第二批POST /v1/debug/task、/v1/debug/query、/v1/debug/node提交调试、查询结果、单节点调试

4. 三者怎样合作：分清两条链路

配置链路：系统知道“用什么、谁能用”

  1. 后台人员在管理端维护工作空间、供应商、模型或应用版本。
  2. 管理端保存与组装相关配置。网关 ConfigCenter 存在获取管理端配置的代码，并按开关与配置源进行合并／刷新。
  3. 在当前源码中，国内分支可通过 getModelConfigMap RPC 获取，海外分支存在 HTTP 获取路径；实际走哪条取决于运行环境。
  4. 网关更新可用的路由、凭证和 Client 等缓存。应用版本发布与工作流配置生效是另一个需要单独追踪的链路。

保存到数据库、组装配置、发布、网关刷新不是天然同一个原子动作。新旧配置源和开关也不能忽略。具体生效时序必须继续沿实现验证。

运行链路：一次业务请求如何得到结果

  1. 业务直接调用网关：网关识别身份、路由并调用厂商，返回普通或流式响应。
  2. 业务调用工作流：执行引擎加载流程、创建当前执行状态、运行节点，模型节点按模型层实现请求网关，最终汇总或流式输出。
  3. 管理端的聊天／调试功能可以作为入口或代理，但不表示每次线上模型请求都先经过管理端。

6. 推荐的源码阅读顺序

  1. 先读本页，只画职责关系，不写代码。
  2. AgentController 的 processOpenai 和 doProcess。
  3. Pipeline.process：先正常流程，再两个 catch。
  4. ModelRouter.route，然后追到一个实际 Client／Processor。
