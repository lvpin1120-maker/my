今天已经讲清楚的部分

  • 追踪字段：这里是 traceId，不是 taskId。传入没有值时生成，有已有值时沿用；当前工具用前缀加 UUID 生成。
  • 鉴权：普通路径根据 API Key 查 business 并写入请求。未知 Key 返回鉴权不通过，Pipeline 抛出对应 SystemException，进入第一个 catch 构造错误响应，不再路由。business 与管理端工作空间是否一一对应尚未核对。
  • 路由：先按 business + model 找供应商列表；再按 business + model + processType 找 ModelProcessConfig。不同业务可以给同一个模型配置不同接入渠道。
  • 处理类型：CHAT 和 CHAT_STREAM 表达普通对话与流式对话，即使模型相同，也需要各自的处理配置。
  • 处理器选择：resolveProcessor 从配置取得 processKey（RESPONSES 协议使用专门配置的 responseProcessKey），再从 processorMap 找对象。它不是直接用厂商枚举选择 execute 的所属类。
  • Client 与 Processor：厂商枚举用于查 Client 管理器；processor 是 execute 的调用对象，Client 管理器是传入参数。执行普通对话时再取得具体 Client。
  • 字段变化：当前 Pipeline.process() 内没有修改 model；另会补充 platformModel、series 等配置。尚未确认全部下游对字段的处理。
  • 学习资料更正：当前 Pipeline 没有独立的限流步骤；普通非流式限流在 ChatProcessor 内，取得具体 Client、熔断判断之后。不要机械记成 Pipeline 内“鉴权→限流→路由”。

证据说明：以上实现关系已根据公司电脑当前源码阅读核对。学习者已自行复述部分主干，并表示理解配置选择；未记录实际运行验证或闭卷完成情况。

回家只做这一小段 · 20～30 分钟

假设本次配置选中的处理器是 AlibabaChatProcessor，这不表示当前环境实际一定使用它。

Pipeline.process()
  → Processor.execute()
    → ChatProcessor.doExecute()
      → ChatProcessor.doExecuteInternal()
        → AlibabaChatProcessor.request()
        ← 得到调用结果
      → 公共收尾与响应处理
  ← 返回响应
  1. 看 Processor.execute() 怎样调用 doExecute()。
  2. 看 ChatProcessor.doExecute() 怎样进入 doExecuteInternal()。
  3. 在 doExecuteInternal() 找到 getMoaiClient()、request()、finalizeNonStream()；暂时只认熔断、限流、超时和计费的位置。
  4. 看 AlibabaChatProcessor.request() 的参数构建、HTTP 调用、响应转换三步。没有业务源码时，用教学例子练同样的父子类调用关系。

验收题：子类没有自己写 execute()，为什么还能调用它？父类执行流程中调用 request()，为什么会进入子类的实现？先自己回答，再让 Codex 核对。
